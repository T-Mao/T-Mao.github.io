Spotify Browser

An Angular and Express project for browsing Spotify artists, albums, and tracks.

Follow a music query through the whole application

I built Spotify Browser from October to November 2022 using Angular and TypeScript on the frontend and Node.js with Express on the backend. The project uses Spotify’s API to search and browse artists, albums, and tracks.

I worked on the interface, typed data models, API service, routes, and authorization flow. The app focuses on catalog discovery and the relationship between search results and detail pages.

Reuse the browsing components

A search view sends the selected category and query through an Angular service to Express. Results appear in reusable artist/album cards or track lists. Detail routes such as /artist/:id, /album/:id, and /track/:id connect those results to deeper views.

Track lists adapt their columns to the context. An album view, for instance, does not need to repeat the same album information on every row. I also worked on visual displays for track audio features, using color-coded bars to make the API data easier to compare.

Keep the external API behind a service boundary

The Express layer handles authorization and requests to Spotify. The login and callback routes exchange an authorization code for tokens, and the token lifecycle includes a refresh path when continued access is needed.

Separating that work from individual Angular components made the data flow easier to understand: a component asks for a resource; a service handles the request; the backend communicates with the provider.

I also explored lazy-loaded routes and caching as ways to defer unused views and reuse data across repeated requests.

API integration

The project was built against Spotify’s 2022 API. Running it with today’s API requires checking the provider’s current access and authorization requirements. Spotify’s token-refresh documentation explains the refresh mechanism.

What I learned

The project gave me practice maintaining a consistent resource model across an external API, a backend, and a component-based interface. It also made failures part of the user flow: a detail view depends on network data and valid authorization, not just a correctly rendered template.
