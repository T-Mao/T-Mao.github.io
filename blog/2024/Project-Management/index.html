Making Changing Requirements Reviewable

Published on October 2, 2024 , last updated on October 5, 2026

2024   ·   project-management   mobile   agile   flutter   ·   mobile-dev

Changing requirements were a regular part of building the consumer and technician apps at SupTech. We were developing a service product while the business was still refining how it should work. My responsibilities included both implementation and helping turn that changing vision into a sequence the team could deliver.

I learned to distinguish two questions: is this new idea useful, and should it enter the work already underway? A request can be worthwhile without being the next thing to build.

Write down the change in behavior

A change request needs more than a title. I want to capture the current behavior, the proposed behavior, the reason for the change, and the conditions for accepting it. Naming the requester and date also helps preserve context when the discussion continues later.

Consider a location-based dispatch change as an example. “Support different service categories” might require changes to profiles, matching rules, the nearby-order feed, maps, and existing records. A dropdown is only the visible part of that change.

A good discussion surfaces the decisions before implementation: can a technician belong to several categories, which radius applies, what happens to old profiles, and should an already accepted order be affected?

Writing these questions down turns a vague request into something people can assess. It also exposes differences in understanding while they are still cheap to resolve.

Treat the schedule as a set of tradeoffs

Short development cycles helped limit how much uncertain work accumulated. The important part was agreeing on what belonged in the current cycle and what could wait.

A scope boundary is useful only if there is a process for exceptions. Urgent defects and a newly discovered business constraint may justify a change. When they do, something else may move. I try to explain that tradeoff concretely: a new matching rule can delay the planned notification work because both touch the order lifecycle and need integration testing.

Making the tradeoff explicit gives stakeholders a real choice.

Isolate changes without losing their dependencies

Feature branches gave larger changes a place to develop while the stable branch remained available for release. Focused commits also made review and recovery easier to reason about. The official Git branching guide describes how topic branches keep related work together.

The following is an illustrative workflow:

git switch -c feature/service-category-matching
# Implement a focused change and review its diff.
git add path/to/changed/files
git commit -m "Add category-aware order eligibility"

Deployed database migrations and shared configuration changes need their own coordination plan alongside the branch. If both old and new app versions will be in use, compatibility becomes part of the acceptance criteria.

Make demos answer specific questions

Internal Android builds and TestFlight builds made product discussions more concrete. A useful demo has a question to resolve: is the order sequence clear, does the technician understand the available action, or is a new category rule represented correctly?

Feedback should then return to the requirement record. Otherwise, the team can accumulate contradictory decisions across screenshots, chat messages, and meetings.

For a location-rule change, I would test a technician inside the radius, outside it, on its boundary, and with no usable location. I would also check an order accepted by someone else during refresh. These cases describe the uncertainty the change introduces.

Use flags for a defined purpose

A feature flag can allow internal evaluation before broader exposure. It needs an owner, a default, a tested disabled path, and an eventual removal decision. Migration safety and backend authorization still need independent validation.

I view flags as one tool among several. A small, compatible change may need no flag at all; a major workflow change may need staged exposure and clearer recovery planning.

Keep the final decision easy to find

After a change is accepted, the record should show the behavior that actually shipped. Old drafts still explain the history, but they should not compete with the current specification.

The record was useful when it let someone answer a practical question: what are we building now, what moved out of this release, and which decision explains that choice? Keeping those answers current helped me turn shifting requirements into changes the team could discuss and test.
