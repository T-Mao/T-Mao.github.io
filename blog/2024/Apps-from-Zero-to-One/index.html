Building Two Mobile Apps Around One Service Workflow

Published on September 4, 2024 , last updated on October 5, 2026

2024   ·   mobile   agile   flutter   fast-delivery   ·   mobile-dev

At SupTech, I was the sole app developer for two Flutter applications built from the ground up: a consumer app for requesting service and a technician app for finding and completing work. Both needed to run on iOS and Android. I had to turn evolving requirements into two clients that agreed about the same service workflow.

The consumer wanted a clear answer to “What happens next?” The technician needed to know “Which action can I take now?” Orders, location, chat, payment, and notifications had to tell a consistent story across both clients.

Choose shared work carefully

Flutter was a practical choice because much of the UI and application logic could be shared across platforms. Authentication, localization, API models, and reusable components offered opportunities to avoid duplicate work.

Shared code worked alongside native responsibilities. Notification permissions, signing, location behavior, and store submission required platform-specific attention and separate end-to-end checks for iOS and Android.

I also needed to distinguish reusable infrastructure from different product decisions. Consumers and technicians could use the same order model while seeing different actions and explanations. Forcing both into identical screens would have saved code at the expense of clarity.

Build the service journey before polishing its edges

With requirements still evolving, I broke the work into connected capabilities: sign in, create an order, find eligible work, accept it, communicate, pay, and complete service. The dependency between those steps determined useful implementation order.

A payment screen without an agreed order lifecycle is hard to validate. A nearby-job map without reliable acceptance rules can look finished while hiding the largest risk. Getting a complete, modest version of the journey working was more valuable than finishing many disconnected screens.

Regular internal builds also made requirements concrete. A stakeholder can give more useful feedback after trying the actual sequence than after reading a list of planned features. Each new idea from that feedback still needs a scope decision and a place in the development plan.

Integrations are product behavior

The apps included Stripe payments, location-based job discovery, chat, notifications, and multilingual interfaces. Each integration introduced a different kind of uncertainty.

For payments, the server needed to establish authoritative transaction state. A completed mobile interaction cannot be the only trigger for fulfillment because the app may close before reporting its result. Stripe’s payment status guidance recommends monitoring the result on the server with webhooks.

For chat, persisted messages and synchronization were separate from push alerts. A notification could invite someone back to a conversation; the conversation still needed to load its history from a durable source.

For location, the interesting work was often outside the map widget: permission denial, stale coordinates, battery use, and the difference between nearby and practically reachable.

For localization, I needed to think beyond translated strings. English, Simplified Chinese, and Traditional Chinese can change line length and layout. Flutter’s internationalization documentation describes the framework support; checking real screens remains part of the work.

Let backend changes stop at a defined boundary

The project involved Node.js/Firebase and later Java/MySQL integration. That made stable client-facing models especially valuable. Keeping API access out of widgets reduced the places that needed attention when endpoints or response shapes changed.

This illustrative example separates API access from the client-facing order model:

class OrderRepository {
  OrderRepository(this.api);
  final OrderApi api;

  Future<List<Order>> nearbyOrders() async {
    final response = await api.fetchNearbyOrders();
    return response.items.map(Order.fromJson).toList();
  }
}

The repository also needs an intentional error contract so the UI can present failures in product terms.

Release the complete flow

A signed binary is one release artifact. The release also depends on configuration, permissions, backend compatibility, store metadata, and a way to investigate problems afterward.

The most demanding part of these apps was keeping the whole journey in view while working through individual screens and integrations. An order could look correct in one client and still leave the other user unsure what to do. Building both sides gave me a practical habit I still use: follow the same action from the first tap to the state the other person receives.
